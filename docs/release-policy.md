# Windows版の配布・更新ポリシー

決定日：2026-10-25 ／ 版数：v0.2

## この文書の位置付け

DC-DesignerのWindows版を配布・更新する際の運用方針。配布運用については、この文書を正本とし、READMEには概要を載せる。

**これは方針の記録であり、配信機能や権限制限の実装完了を意味しない。** この文書の追加時点では、Electronによるパッケージ化、インストーラー、自動更新、配信ワークフロー、`release` ブランチの作成やGitHub側の権限設定は行っていない。

## ブランチと公開の条件

| 対象 | 役割 | 正式配信 |
| --- | --- | --- |
| `feature/*` など | 個別の開発・修正。確認後に `main` へ取り込む | しない |
| `main` | 日常の開発・統合・動作確認 | push・マージだけではしない |
| `release` | 配布する時点の `main` をマージし、配布前の確認を行う | push・マージだけではしない |
| `v1.0.1` などのバージョンタグ | `release` 上で確認済みの配布対象コミットを固定する | 本人の承認と検証成功を条件にビルド・公開する |

- 基本は **`main` → `release` のマージ**とし、変更を選別するためのチェリーピックは原則使わない。
- 未完成の機能は `feature/*` に置くなど、配布してはいけない変更を `main` に混ぜない。`main` に未完成の変更が残っている場合は、完成・無効化などの対応が済むまで配布しない。
- タグはリモートの `release` の履歴に含まれる、配布前の確認を終えたコミットだけに付ける。配布CIでもこの条件とバージョンの一致を検証する。
- 公開済みタグの付け替えや、同じバージョンの配布物の差し替えはしない。修正は新しいバージョンとして公開する。

## 正式配信できる人

**正式配信の権限と最終承認は、リポジトリ所有者の @itiwoja 本人だけが持つ。** 開発への参加と、公式配布物を公開する権限は分ける。

- `release` への取り込み、配布対象の決定、バージョンタグの作成・push、正式公開の承認は本人が行う。
- GitHub Actionsは、本人の承認を受けたビルド・公開処理だけを代行する。第三者のpush、PR、マージ、手動実行だけで正式配信されてはいけない。
- AIエージェントも、変更や文書化の依頼だけでタグのpush・公開・権限変更を行わない。実際の配信には本人の明示的な依頼・承認が必要。

### GitHub側で実装時に設定する制限

READMEや `CODEOWNERS` の記載だけでは、配信権限は制限できない。正式配信を始める前に、次の制限を設定・検証する。

| 対象 | 必要な制限 |
| --- | --- |
| `release` | ブランチのRuleset等で更新できる主体を本人に限定し、強制push・削除も防ぐ |
| 配信用タグ `v*` | タグのRuleset等で作成できる主体を本人に限定し、公開済みタグの更新・削除も防ぐ |
| 配信ワークフロー | タグ・バージョン・配布対象コミットを検証し、起動・再実行したアカウントも本人に限定する |
| 配信用Environment（例：`production-release`） | 承認者を本人だけにし、正式公開ジョブに承認を必須化する。本人が起動した実行を本人で承認できる設定にし、承認なしの実行・バイパスを許可しない |
| ワークフローと運用設定の変更 | 本人の確認なしに、配信経路・承認条件・認証情報の参照先を変えられないようにする |
| 認証情報・署名情報 | 公開に使える資格情報は承認後の公開ジョブだけで利用する。通常の検証ジョブは原則読み取り専用とし、PR由来の未確認コードに公開用の秘密情報を渡さない |
| Releasesの直接操作 | Releasesや更新ファイルを直接作成・変更できる権限や資格情報も、本人と承認済み公開ジョブだけに限定する |

- Environmentの承認はCIの公開ジョブを制御するものであり、Web画面やAPIからの直接公開まで禁止するものではない。第三者へのリポジトリのWrite / Maintain / Admin権限、`contents: write` 相当のGitHub App・PAT等の付与は、配信権限を与えることにつながるため避ける。外部協力者は原則fork・PRで参加する。
- 本人以外のバイパス権限・チーム・Appや、承認を通らず公開できる別ワークフロー・トークンを残さない。将来権限を変更する場合も、この条件を再確認する。
- GitHubのプランやリポジトリの公開範囲によって利用できる保護機能が異なる。同等の制限を用意できない場合は、配信を開始せず構成を見直す。
- 配布アプリに開発者用PAT・署名用秘密鍵・開発者のAPIキーなどを埋め込まない。

## 1回の配信手順

以下は実装後の運用手順。現時点でタグをpushしてもWindows版の配信は行われない。

1. `main` の変更・テスト結果を確認し、配布可能な状態にする。
2. 本人が `main` を `release` にマージする。初回は、配布対象の `main` から `release` を作成する。
3. アプリのバージョンを上げる（例：`1.0.0` → `1.0.1`）。`package.json` と `package-lock.json` など、関連するバージョンを揃える。
4. 型チェック・テスト・ビルドに加え、実際のWindowsで起動、サインイン、保存、旧版からの更新を確認する。配布物に秘密情報・個人データが入っていないことも確認する。
5. 確認したコミットを `release` にpushする。この時点では正式配信しない。
6. 本人がそのコミットに `v1.0.1` などのタグを付けてpushする。
7. GitHub ActionsがWindows版のビルド・検証を行う。本人が配信用Environmentで承認し、公開ジョブがインストーラーと `latest.yml` など必要な更新用成果物を公開する。配信先の第一候補は公開GitHub Releases。
8. 公開したバージョン、配布物、更新情報を確認する。`release` で追加したバージョン変更・修正は `main` にもマージし、次の開発と同期する。

不具合の修正も原則 `main` で行い、同じ手順で新しいバージョンを配信する。例外的に `release` で修正した場合も、必ず `main` に反映する。

## 利用者側の更新

- 同梱する画面・サーバー・認証処理は、新バージョンのアプリとしてまとめて更新する。GitHubへのソースコードのpushを、利用者のアプリが直接取り込む方式ではない。
- **インストール済みのWindows版は、アプリを起動するたびに公開済みの正式版を確認する。** 確認はバックグラウンドで行い、画面表示や編集開始を待たせない。同一プロセス内の画面遷移・再読み込みでは確認を繰り返さない。
- 現在より新しい正式版がある場合は、**アプリ内の更新案内ポップアップ**を表示する。現在・最新バージョン、更新内容と「更新する」「あとで」を示す。最新版の場合はポップアップを出さない。
- 「更新する」を選んだ後にだけアプリ内でダウンロードする。「あとで」や閉じる操作は今回だけの保留とし、同じ更新でも次回起動時に再確認・再通知する。恒久的な非表示や無断ダウンロードは行わない。
- ダウンロード完了後に「保存して再起動」「あとで」を表示する。利用者が再起動を選び、全編集内容・保留中の保存の完了と、生成・書き出し等の処理が動いていないことを確認してから適用する。保存失敗時・確認できない場合は再起動しない。
- ダウンロード済みでも、通常の終了・次回起動だけでは勝手に適用しない。次回起動時は公開情報とキャッシュの有効性を確認し、利用者の再起動操作を待つ。強制更新・強制再起動は行わない。
- オフライン、確認のタイムアウト、配信先の障害があっても通常起動・編集を続けられる。「確認できなかった」と「最新版」を区別し、確認失敗だけで起動時のエラーポップアップを出さない。
- 資料・画像・設定・認証情報はプログラムの配置先と分離し、通常の更新では維持する。認証失効時などは再ログインが必要になる。
- 更新に失敗した場合は利用者に知らせ、既存データ・既存アプリをできる限り維持する。データ形式の変更時はバックアップと移行処理を用意する。
- 不具合版の配信停止や復旧版の公開も本人の承認で行う。公開済みタグの付け替えや、利用者データの無条件な巻き戻しは行わない。

画面、状態遷移、プロセス間通信、保存確認と受け入れ条件は [起動時の更新確認・ポップアップ設計](./desktop-update-design.md) を参照。今回の変更は設計のみで、更新機能は未実装。

## 配信開始までに残っていること

- Electron、Windowsインストーラー、自動更新、ユーザーデータの分離・保護の実装。
- `release` ブランチ、バージョン管理、タグを起点とするビルド・公開CIの準備。
- 上記の権限制限と承認設定、および本人以外では公開できないことの検証。
- 配信先・公開範囲・コード署名方式の確定。非公開配信の場合は安全な取得方法を別途設計する。
- 実機での新規インストール・旧版からの更新・失敗時の挙動・データ維持の検証。
