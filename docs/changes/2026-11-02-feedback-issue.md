# アプリ内から要望・不具合を送る機能を、GitHub の Issue 作成画面を開く方式にする（2026-11-02）

決定者：ユーザー（Issue #59、方式は「ブラウザで起票」を選択）

## なぜ

利用者が要望や不具合をアプリの中から伝えられるようにしたい、という依頼。送り先は、[プライバシー](../privacy.md)の「お問い合わせ」と同じ GitHub の Issues にする。

送り方は次の 2 つを比べた。

- 中継サーバーで直接起票する：サイトは GitHub Pages の静的サイトで、中継先が無い。サーバーの運用、スパム対策、シークレットの管理、プライバシーポリシーの改訂が要る。
- ブラウザで起票する：アプリは通信せず、利用者が自分の GitHub アカウントで Submit する。サーバーもトークンも要らない。

ユーザーが後者を選んだ。

## 何を変えたか

- アプリ内にフォームを足す。エディタ左下のボタン、または製品版の「ヘルプ → 要望・不具合を送る…」から開く。
  種類（要望・不具合・質問）、件名、内容、「アプリの版と OS を添える」（既定でオン）を入れる。
- 「GitHub で送る」を押すと、件名と内容を入れた `https://github.com/itiwoja/DC-Designer/issues/new` を既定のブラウザで開く。
  アプリ自身は通信しない。外部通信の許可リスト（`server/egress.ts`）は変えない。
- 製品版では、画面の https の外部リンクを `shell.openExternal` に渡す既存の処理（`desktop/main.ts` の `setWindowOpenHandler`）で開く。
- 送るかどうか、どのアカウントで送るかは、ブラウザの GitHub 上で利用者が決める。書いた内容は公開される。
- [プライバシー](../privacy.md)に、通信しないこと、添えるのは版と OS だけであること、内容が公開されることを書いた。
  「外へ送るのは 4 つだけ」という約束は変えていない。

## 確かめたこと

- `npm run typecheck`、`npm test`（72 ファイル・722 件。URL の組み立ては `tests/feedback.test.ts`）、`npm run build` が通る。
- 開発版のエディタをヘッドレスの Chromium で開き、左下のボタンでフォームが開くこと、「不具合」を選ぶと本文の雛形が入ること、
  件名に `&` `#` を含めて送ると `github.com/itiwoja/DC-Designer/issues/new` の `title`・`body` に崩れずに入ること（環境節つき）、
  送ったあとと Esc でフォームが閉じることを見た。
- 製品版（Electron）での「ヘルプ → 要望・不具合を送る…」と、既定のブラウザで開くところは、実機では確かめていない。

## 採らなかったもの

- 中継サーバーで直接起票すること：上の「なぜ」のとおり、運用とプライバシーポリシーの改訂が要るため。
- アプリに GitHub のトークンを入れて、API で直接起票すること：アプリに入れたトークンは取り出せるため。

## 既知の制限

- 送るには GitHub のアカウントが要る。アカウントの無い利用者は、Issue を作れない（[GitHub の Issues](https://github.com/itiwoja/DC-Designer/issues) を直接見ることはできる）。
- 件名と本文は URL に入るため長さに上限を置く。本文は 6000 文字、件名は 200 文字で切る。切れた分は Issue に入らない。
- ラベルは付けられない。Issue のラベルを URL の `labels` で指定しても、書き込み権限の無い利用者には効かないため。
- 書いた内容は公開される。利用者の作品や個人情報は、フォームに入れないよう案内する必要がある。
- 製品版の窓は `titleBarStyle: "hidden"`・`autoHideMenuBar: true` のため、メニューバー（「ヘルプ」）が Windows で見えるかは実機で確かめていない
  （既存の「ヘルプ → 更新を確認」も同じ）。見えなくても、エディタ左下のボタンから開ける。
